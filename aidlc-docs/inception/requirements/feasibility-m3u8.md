# m3u8（HLS）対応の実現可能性評価

**対象**: インターネット上に置かれた m3u8（HLS プレイリスト）が指す動画のダウンロード
**評価日**: 2026-09-21
**位置づけ**: INCEPTION - Requirements Analysis の前段。要件を確定する前に「現実的に実行可能か」を判定するために作成した

---

## 結論

**実行可能。** ただし「m3u8 対応」と一口に言うものの中身は難易度の異なる 3 層に分かれ、
**第 1 層はすでに動いており、第 3 層は既存の停止機構の欠陥を露出させる**。

| 層 | 内容 | 判定 | 必要な作業量 |
|---|---|---|---|
| **第 1 層** | 素の VOD m3u8 URL のダウンロード | ✅ **すでに動く** | **ゼロ**（実装不要） |
| **第 2 層** | 現実のサイトで通すための補強（Referer・ファイル名・期限切れ案内） | ✅ 容易 | 小（引数 1 個 + 命名規則 + UI 文言） |
| **第 3 層** | ライブ配信の録画（停止してそこまでを保存） | ⚠️ 可能だが重い | 大（**既存バグの修正が前提**） |

---

## 検証方法

ローカルに HTTP サーバ（`python3`）を立て、実サイトによくある配信条件を再現した。
素材は ffmpeg で生成した合成テスト映像（`testsrc` + `sine` トーン）で、実在コンテンツは一切使っていない。

実行した yt-dlp の引数は **[buildYtDlpArgs](../../../download.go) が組み立てるものと同一**にした（`--retries 10`
`--fragment-retries 10` `--abort-on-unavailable-fragment` `--socket-timeout 30`
`-f bestvideo+bestaudio/best` `--merge-output-format mp4` など）。つまり以下は「現行アプリが
その URL を渡されたらどうなるか」の再現である。

## 実測結果

| # | シナリオ | 結果 | 備考 |
|---|---|---|---|
| 1 | 素の VOD（master playlist） | ✅ 成功 | `[hlsnative] Total fragments: 3` → `[FixupM3u8]` → mp4 生成 |
| 2 | 素の VOD（media playlist 直指定） | ✅ 成功 | master を経由しなくても同じ |
| 3 | **AES-128 暗号化 HLS** | ✅ 成功 | `#EXT-X-KEY` の鍵 URI を yt-dlp が自動取得して復号した |
| 4 | **映像・音声が別レンディション**の master | ✅ 成功 | `bestvideo+bestaudio` が両方を取り `[Merger]` で結合 |
| 5 | **Referer 必須**のサーバ | ❌ 403 | `ERROR: Unable to download webpage: HTTP Error 403: Forbidden` |
| 6 | 同じサーバに `--referer` を付与 | ✅ 成功 | **引数 1 個で 403 が解消した** |
| 7 | **期限切れ URL**（トークン失効後） | ❌ 403 | 同じエラー。**技術的な対策は存在しない** |
| 8 | 断片 1 つだけ 403（断片欠損） | ❌ エラー | 10 回リトライ後に `fragment 2 not found, unable to continue`。設計どおりの挙動 |
| 9 | **ライブ**（`#EXT-X-ENDLIST` なし） | ⚠️ 自然終了しない | かつ **ffmpeg 子プロセスに委譲される**（下記） |

### 注目点 1: AES-128 暗号化は障害にならない

Web の HLS はかなりの割合が AES-128 で暗号化されているが、これは yt-dlp が透過的に処理する。
鍵 URI から鍵を取得して復号するところまで実測で確認した。**DRM（Widevine / FairPlay）は別物で、
これは yt-dlp でも復号できず対象外**。`has_drm` フラグで判別できる。

### 注目点 2: 期限切れ URL は「登録のみモード」と最悪の相性

m3u8 の URL は有効期限トークン付きのことが多い。シナリオ 7 のとおり、期限が切れた URL は
何をしても 403 で、**ユーザーが URL を取り直す以外の対策はない**。

問題は本アプリの既定が **同時ダウンロード数 0（登録のみモード）**
（[requirements.md](requirements.md)「同時ダウンロード数 0」）である点。URL を登録して
キューに寝かせておく運用が既定なので、**寝かせている間に URL が失効する**。
さらに URL にトークンが含まれるため、取り直した URL は文字列が変わり、
既存の重複登録防止（完全一致）も効かない。

これは実装で直せる話ではないが、**ユーザーに事前に伝えられるかどうかで体験が大きく変わる**。

### 注目点 3: ライブ HLS は ffmpeg 子プロセスに委譲される（既存バグを露出させる）

ライブ判定された m3u8 について、yt-dlp は hlsnative を使わず **ffmpeg を子プロセスとして起動**し、
そちらにダウンロードを任せる。実測したプロセスツリー:

```
PID 57658  yt-dlp ... -- http://.../live.m3u8
PID 57660   └─ ffmpeg -y -hide_banner -headers ... -i http://.../live.m3u8 -c copy -f mpegts file:.../aabbccdd.mp4.part
```

ところが本アプリの停止・一時停止はすべて `item.cmd`（= **yt-dlp のプロセスのみ**）を対象にしている。
そして [applyOSProcAttr](../../../sysproc_other.go) は **非 Windows では何もしない no-op** で、
プロセスグループを作っていない（Windows 側も `HideWindow: true` だけで Job Object を使っていない）。

**決定的な実測:**

```
yt-dlp PID=57658 / 子 ffmpeg PID=57660
--- yt-dlp だけに SIGKILL（アプリの CancelDownload と同じ）---
yt-dlp: 死亡
ffmpeg : ★生存（PPID 1 の孤児となり、取得を続けている）
```

つまり現状:

| 操作 | 実際に起きること |
|---|---|
| キャンセル（`Kill`） | yt-dlp だけ死に、**ffmpeg は孤児化して裏で帯域を食い続ける**。workDir を `RemoveAll` しても書き続ける |
| 一時停止（`SIGSTOP`） | yt-dlp だけ止まり、**ffmpeg はダウンロードを続ける**（止まっていない） |
| yt-dlp の更新（`killRegisteredProcs`） | 同じ。`waitProcsDrained` は yt-dlp の生存だけを見るため、**ffmpeg が掴んだままでも「排出完了」と判定する**（Windows では実行ファイル置換が共有違反で失敗しうる） |

**★ これは m3u8 やライブに限った話ではなく、今日すでに存在する不具合である。**
VOD でも `[Merger]` / `[FixupM3u8]` の最中にキャンセルすれば同じ経路を通る（後処理は短命なので
目立たないだけ）。ライブ m3u8 は ffmpeg の生存時間を数時間に伸ばすため、**既存の穴を露出させる**。

この事象は [design.md](../application-design/design.md) の
「停止対象は『実行中』だけでは足りない」で列挙された 3 経路に **4 番目として漏れていた**ものである
（同節は yt-dlp プロセスの取りこぼしは網羅したが、yt-dlp が産む**孫プロセス**を扱っていない）。

### 注目点 4: 中断した VOD は救済できるが、ライブは救済できない

「停止してそこまでを保存」の実現可能性は、中断時に残るファイルが使えるかで決まる。実測すると**真逆**だった。

| ケース | 残るファイル | 再生可能か |
|---|---|---|
| **VOD**（hlsnative が書く `.part`） | 59,220 バイト | ✅ **可能**。`ffprobe` が `format_name=mpegts` / `duration=2.02` と読めた。`ffmpeg -c copy` で再生可能な mp4 に救出できた |
| **ライブ**（ffmpeg が書く `.part`） | **0 バイト** | ❌ **不可能**。`ffprobe` は `Invalid data found`。SIGKILL ではバッファがフラッシュされない |

したがって:

- **VOD の「停止して保存」は現実的** — `.part` を救出リマックスすれば成立する
- **ライブの「停止して保存」には ffmpeg への graceful stop が必須** — SIGINT / SIGTERM（または stdin へ `q`）を
  **孫プロセスの ffmpeg に**届ける必要がある。SIGKILL では必ず 0 バイトになる

## 推奨スコープ（3 段に分ける）

実測に基づく推奨は **「第 1 段を今回の要件とし、第 2 段を独立した要件として立てる」**。

### 第 1 段: m3u8 を実用にする（今回やる価値が高い）

小さく、効果が実測で確認済み。既存の停止機構に触らないため回帰リスクが低い。

1. **Referer を渡せるようにする** — シナリオ 5→6 のとおり `--referer` 1 個で 403 が解消する
2. **保存ファイル名の規則を決める** — HLS にタイトルのメタデータがないため、現状は全部
   `master.mp4` / `index.mp4` に集中し、2 本目以降が `master (1).mp4` になって判別不能
3. **期限切れ URL の案内** — 直せないが伝えられる。とくに既定が「登録のみモード」であることとの
   組み合わせを警告する価値がある

### 第 2 段: 子プロセスの孤児化を直す（m3u8 とは独立した既存バグ）

注目点 3 の修正。**m3u8 対応とは切り離して独立の要件にすべき**で、優先度は第 1 段より高い可能性がある
（ライブを扱わなくても後処理中のキャンセルで発生しうるため）。

対策の方向: 非 Windows は `Setpgid: true` でプロセスグループを作り `Kill(-pgid)` で一括停止、
Windows は Job Object に入れる。どちらも `applyOSProcAttr` の既存の抽象に収まる。
`applyOSProcAttr` は「1 箇所でも漏れたらその経路だけ穴が空く」ルールとして
[design.md](../application-design/design.md) に既に明文化されている。

### 第 3 段: ライブ録画の「停止して保存」（やるか決める）

**第 2 段が前提**。加えて graceful stop（SIGKILL ではなく SIGINT/SIGTERM）と、
ライブでは意味を持たない進捗率（`duration` が `null`）の UI 表現の設計が必要。

---

## 対象外（技術的に不可能なもの）

- **DRM 保護されたストリーム**（Widevine / FairPlay / PlayReady）— yt-dlp でも復号できない。`has_drm` で判別可能
- **期限切れ URL の自動復活** — ユーザーが元ページから URL を取り直すしかない
